# 運営・障害対応手順
更新：2026-10-14。対象：にっぽんマップ。単独運営向け。

## 監視
GitHub Actions Quality checksはpushと既存の定期実行で型・ビルド・機能テスト・本番API・SEOを検査。
Production health and SEOは毎日02:17 UTC（11:17 JST）、手動実行、検査スクリプト／ワークフロー変更時のmain pushで実行。
失敗時はActionsの赤い実行を開き、FAILに続くルート・ステップを確認。メール通知の設定状態は未確認。外部通知先や架空の当番を追加していない。
監視自体の障害検出はtests/production-health.test.cjsで通信全失敗と空サイトマップを注入し、終了コード1を確認する。これは本番障害を起こさない。
設定済みのcronと実際のcron成功は別。初回定期実行が成功した日時を記録してから定期動作確認済みにする。

## 障害切り分け
1. 発生時刻（JST）、公開URL、カテゴリ・地域・検索語、PC／スマホ、直前のコミットを記録。連絡先や入力内容を公開ログへコピーしない。
2. トップ・地図・施設APIの応答を比較。WebGL非対応による地図失敗はAPI障害と分ける。
3. Vercelの対象コミットのデプロイとGitHub CIを確認。古いERRORを最新デプロイと混同しない。
4. Supabase状態とAPIエラーを確認。キーを公開ログへ出さない。
5. コードが原因なら最小修正か既知の正常コミットへの再デプロイを選ぶ。DB復元はコードの巻き戻しと別であり、安易に本番restoreを行わない。
6. 検査を再実行し、元の再現操作を本番で確認。GitHub成功だけで終了しない。

## データ更新
変更前に対象ID、更新項目、公式根拠、旧値、件数と復旧方法を保存。住所・座標・URLは推測で補完しない。
UPDATEは対象IDと想定旧値をWHEREで固定し、トランザクションを使用。RETURNINGと件数を確認。0件や想定外の件数なら次の更新へ進まない。
更新後、元の検索・地域フィルターと施設詳細を確認。公開APIのキャッシュ反映も確認する。
今回6施設の修正はfacility-corrections-2026-10-14.jsonと対応rollback SQLに旧値を残す。これは全DBバックアップではない。

## バックアップ・復旧の未確認事項
プロジェクトACTIVE_HEALTHYは確認済みだが、契約プラン・保存済みバックアップ日時・保持期間・PITR有効化は、この接続で確認できていない。
公式資料：https://supabase.com/docs/guides/platform/backups
無料プランでは定期エクスポートと別保管先の確保が必要。有料プランのバックアップ保持を契約未確認のまま適用しない。
DBバックアップにはStorageオブジェクトの実体が含まれないため、使用しているオブジェクトは別に保管状態を確認する。
本番復元は停止や更新後データの喪失を伴い得る。復旧実験は隔離環境へ復元してから行う。新規有料環境や有料PITRは承認前に契約しない。

復旧試験で必要な証拠：
- バックアップの作成日時・対象範囲・チェックサム・秘密でない保管先識別。
- 隔離先でカテゴリ別有効／非公開件数、主要施設の項目、RLS・権限・公開RPCが一致。
- 投稿と利用計測の権限・保存状態、Storageファイル、アプリ環境設定も確認。
- 測定した復旧時間と復元点、それ以降に失われる更新範囲を記録。
- 本番切替は別の判断として扱う。現時点の復旧試験は未完了。

## 投稿審査
既存docs/place-submission-review-workflow.mdに従い、根拠URLを確認してpending投稿を審査する。
未確認情報は承認しない。連絡先は公開しない。投稿の送信だけで施設公開へ直結させない。

## 週次確認
Search Consoleのサイトマップ、ページ登録、検索パフォーマンスを同一日付範囲で記録。現在のクラウドブラウザは未ログインの案内画面までで、私有レポートは未確認。
利用計測はユーザー数ではない。検証実施日・検証イベントを別記して、運営操作が利用増加として混ざらないようにする。
